Decisions confirmed or made as of 2026-06-21.

**Architecture:**
- <a id="d-001"></a>Technology stack: determined by Phase 0 — no pre-commitment to TypeScript/Azure or Django/AWS
- <a id="d-002"></a>API surface: REST (ingestion/ops) + GraphQL (consumer 360° queries) — dual layer, not either/or
- <a id="d-003"></a>Batch pipeline orchestration: Apache Airflow replaces SSIS
- <a id="d-004"></a>Database: PostgreSQL + RLS — RLS is the **confirmed multi-tenant isolation mechanism** (Leo 2026-06-21; see the sub-bullet below and `wiki/Privacy-by-Design.md`) that the 2026-06-13 architecture builds on (resolver above RLS, tenant-scoped serving). The policy layer (values) stays with Alicia + Luis. See `docs/consent-pii-erasure-options.md`.
  - **Updated 2026-06-21 (Leo):** RLS confirmed as the isolation mechanism with documented rationale and tradeoffs (research-backed) in `wiki/Privacy-by-Design.md` — shared-database/shared-schema + RLS, tenant context via `app.current_tenant` GUC per transaction, `FORCE ROW LEVEL SECURITY` on owner roles, `BYPASSRLS` reserved for narrow maintenance. Visibility computed from per-fact provenance (set, not owner). Acknowledged tradeoff: RLS isolates rows, not compute/cache/disk (resource fairness is an app-tier concern, not an isolation gap). RLS (access control) and the PII vault (erasure) are orthogonal and compose. The policy layer remains with Alicia + Luis + DAS Legal.
- <a id="d-005"></a>All-tables-from-day-1: the full data model (including AI/ML stubs) deploys in Stage 1 — zero schema migrations for Phase 2. Table count is whatever the model needs, set by the data-model design and not yet scoped; the "19 tables" in DAS's v4 MVP spec is a historical sketch, not our target.
- <a id="d-006"></a>Identity: CVH hash is fully replaced by CDP identity resolution — not extended
- <a id="d-007"></a>**Infrastructure sizing: dev baseline + dynamic scaling (decided 2026-06-16).** Not gating on DAS volume/profile data (not expected, and not a blocker). The stack is elastic — RDS scale-up + Proxy/read-replicas, Redshift Serverless, EKS autoscaling, S3 — so Phase 1 provisions a dev baseline (single-AZ RDS, no replicas, minimal Serverless, small node group) and rightsizes production once real load is observed (a config change, not a redesign). The system surfaces its own profile in flight. Closes the DAS data-profile action item.
- <a id="d-008"></a>**Raw-data buffer / staging layer (decided 2026-06-18, Leo).** Raw ingested data lands in a **raw/staging buffer** — object storage, **parquet** (the bronze layer) — and **dehydration happens from there**. The raw/parquet layer is where analytical processing runs: **Glue (AWS) / Azure equivalent** (Synapse / Data Lake Analytics) over the parquet. **Cross-store erasure must propagate across all layers**: ingest -> raw/staging buffer -> dehydrated -> CDP. Cloud-portable: raw parquet in object storage is portable; the query engine over it is cloud-specific but swappable (Glue is AWS-only — not in scope if Azure; use the Azure equivalent).
- <a id="d-009"></a>**Data-lifecycle / dehydration mechanism: time-partition + rotate out (decided 2026-06-18, Leo).** Append-only and observation tables (the consent ledger, the `event` time spine, identity/attribute history) are **range-partitioned by time (year/month)**. Old partitions rotate to the **dehydrated tier** — detach + archive to cold object storage (S3 / Azure Blob) — and **re-hydrate on demand** (re-attach/restore). Realizes the `active -> raw -> archived -> dehydrated -> erasure` lifecycle (`11-tiered-data-lifecycle.md`). Cloud-portable: Postgres native declarative partitioning + object storage, no proprietary service. Keeps hot tables small without losing history.
- <a id="d-010"></a>**Field Catalog v1 prioritization — LOCKED 2026-06-19 (Alicia Salazar).** 14 of 27 fields are **valuable-now** (Phase 1 build target); 13 are **interesting-later** (Phase 2+). (The lock enumerated 14 valuable-now fields; the original "13" headline was a miscount of the enumerated list — corrected 2026-06-21.) Valuable-now: fields 1–7, 9–11, 13, 15, 23, 24 — identity/vehicle/purchase core (name, email, phone, VIN, year/make/model, purchase date), mileage (at-sale snapshot), vehicle condition (derived from deal type), completed services (validate DMS feed), equity + market value (BlackBook). Interesting-later: trim level (partial dealer coverage), purchase price (dealer access unconfirmed), declined services (messy ETL), open recalls (RecallMasters — new vendor integration), OEM maintenance schedule, completed recalls, services w/ media, service coupons, service/warranty plan offerings, upgrade options, insurance provider + quotes (no source today). Full table in `docs/cdp-field-source-matrix.md` (Phase column).
- <a id="d-011"></a>**Cross-store erasure orchestration: Temporal workflow saga — APPROVED 2026-06-19 (Alicia, Privacy-by-Design).** Full crypto-shred saga runs as a single durable Temporal workflow: destroy DEK (DynamoDB) → evict plaintext DEK (Redis) → purge Postgres → purge S3 bronze → purge Redshift → purge OpenSearch → write erasure audit. Built-in retries, idempotency, single auditable completion record. Temporal already in stack as app-layer orchestrator. Same workflow covers key rotation and re-encryption. See `docs/consent-pii-erasure-options.md` Option C2.
  - **Mechanism superseded 2026-06-21 (Leo) — orchestration approval stands.** The saga's underlying mechanism is no longer crypto-shred / per-consumer DEK; it now drives the PII-vault row delete (see next bullet). The Temporal orchestration pattern Alicia approved is unchanged — only the first step changes (delete deletable vault rows + write tombstone → confirm tokens dereference to nothing across stores → write audit). The DynamoDB DEK-store / Redis DEK-cache / per-store PII purge steps drop away, because PII lives only in the vault. The mechanism change was shared with Alicia + Luis on 2026-06-21 as a **heads-up (informational, not a gate)**; the decision stands and any feedback is incorporated when it arrives.
- <a id="d-012"></a>**PII erasure mechanism: tokenized reference vault + delete-the-row — DECIDED 2026-06-21 (Leo), supersedes per-consumer DEK / crypto-shred (`docs/consent-pii-erasure-options.md` Option set A).** Per-person encryption keys are rejected: too complex, brittle, and expensive (10M+ wrapped-key rows, decrypt-on-every-read + isolated DEK cache infra, cache-coherence and accidental-erasure risk, and the GLBA partial-deletion key-granularity problem). Instead: identity-class PII (name / email / phone / address) is centralized in a single mutable **PII vault** keyed by a surrogate token; the append-only observation/event log, bronze parquet, analytics, and OpenSearch store **tokens + non-PII provenance only, never raw values**. Erasure = delete/null the vault row(s) — tokens elsewhere dereference to nothing, so there is **no cross-store PII purge to propagate** (also removes the Redshift-specific propagation problem; analytics stays Postgres-centric/portable per the Azure-primary / portable-OSS-core stance). **Provenance/lineage for PII is retained** (Leo's explicit requirement): the observation log keeps which source supplied each field, when, and by what method, referencing the value by token — erasing the value leaves "phone provided by DMS on 2026-01-01 via batch" intact. **Scoped GLBA / legal-hold deletion** is plain row selection on source + purpose (no sub-keys; dissolves the prior open key-granularity decision). **Backups** age out by retention policy, not fast purge — deletion policy means not-retained-forever, not delete-immediately. **Optional defense-in-depth (feature-flagged, per-record, off by default):** per-row salt (stored in the row) + a single external pepper (secrets manager) derive a per-row protection key via KDF — DB-dump / backup protection with one secret, not per-person keys; a per-row scheme marker lets plaintext and hardened rows coexist and the flag flip on/off without schema change; hardened-row ciphertext is intentionally non-matchable (matching is on normalized tokens in the identity graph); pepper / derived keys may be cached in an isolated Redis (short TTL, separate from app cache, evicts on erasure) to avoid a secrets/DB round-trip per decryption. **Pepper-clear** is a coarse kill-switch: clearing the pepper makes every value derived from it unreadable at once — global, or per-tenant if the pepper is scoped per tenant (leaning per-tenant for clean dealer offboarding); all-or-nothing, ignores legal holds, so for decommission / offboard / breach only. **Decided 2026-06-21:** pepper scope is **per-tenant by default**, configurable to global (a setting resolved via the policy-config layer). The **policy values** (retention periods, consent taxonomy, lawful basis, suppression scope) are populated by Alicia + Luis; DAS Legal is not a Phase-0 blocker — they approve the proposal once authored. Documented in `wiki/Privacy-by-Design.md`.
  - **Ingest tokenization boundary — tokenize at the CDP, not at the edge (2026-06-21, Leo).** Identity is resolved *inside* the CDP; source systems and the ingest edge carry fragmented single-vector views (much lower re-identification risk — risk concentrates at resolution). Tokenize on ingest **into the CDP only** — extract PII to the vault, leave tokens in the CDP's own stores (observation log, golden record, analytics, search). Do **not** put a tokenization barrier in front of **block storage or event processing** — excessive decentralized coordination on the hottest paths for little benefit on already-fragmented data. Three zones: (1) ingest edge — event bus/stream + raw bronze parquet landing, raw + fragmented, governed by bounded retention/age-out + access control, no per-request delete propagation; (2) CDP boundary — tokenize on ingest; (3) CDP resolved layer — vault holds raw PII, everything else holds tokens, erasure honored here by vault-row delete. Deletion posture: precise delete where identity is concentrated (CDP), retention/age-out where data is fragmented (edge). Honest caveat: a raw edge fragment (e.g. raw email in bronze during its retention window) is still PII under CCPA/TDPSA — defensible via bounded edge retention + fragmentation + access control + precise resolved-record deletion (same shape as backup age-out); DAS Legal approves at proposal stage, not a Phase-0 blocker; per-source edge tokenization can be enabled via the policy-config layer for high-sensitivity sources.
  - **Offer both mechanisms; vault is default (2026-06-21, Leo).** We can present both crypto-shred and vault; vault (delete-the-row) is the default/recommendation. Crypto-shred stays available where a source/contract demands cryptographic erasure, but its decentralized coordinated cross-store delete is **excessive for this architecture** (centralizing PII removes the scattered-PII condition it solves). Offering both is a per-scope policy choice, not two parallel builds.
  - <a id="d-117"></a>**Resolver blocking-key boundary (2026-06-21, Leo).** The `person` shell carries pseudonymous one-way blocking keys (email/phone hashes, metaphone, zip) *outside* the vault because deterministic matching needs them queryable. They are not vault PII, but they are a re-identification path — so **erasure scrubs the email/phone hashes** alongside the vault delete; the `person_id` shell + tokenized history remain for bitemporal integrity. Acceptable boundary.
  - **Policy-config layer needed (raised 2026-06-21, Leo; spec TBD).** The salt+pepper toggle — and retention, tiering, suppression scope, edge-tokenization — are configurable per **source / channel / partner / dealership / user**. A single record matches several scopes at once, so a policy-config layer with deterministic resolution is required (most-restrictive-wins for protection/retention obligations, regulatory floor non-overridable; explicit per-scope settings). We build the config layer + resolver + admin surface; Alicia + Luis + Legal populate the policy values. Candidate spec: `specs/03-phase-1-build/03-backend-data-model/18-policy-config-layer.md` (next free number).
- <a id="d-013"></a>**Consent-ledger mechanism: portable, application-built, append-only hash-chained (decided 2026-06-18, Leo).** The consent/suppression ledger is built in-application (SHA-256 hash chain), **cloud-portable** — deploys identically on Azure AKS or AWS EKS, no cloud-KMS-specific signing (avoids coupling to AWS KMS / Azure Key Vault). Any signing uses a portable mechanism (app-held key / HMAC). Consistent with the portable-OSS-core / Azure-or-AWS stance; the same portability principle extends to crypto-shred key management (cloud-agnostic KMS abstraction, not a specific cloud KMS). Resolves the consent-ledger open question (1 of 4 open consent-enforcement items); the policy layer, cross-store erasure orchestration, and event-sourced-artifact access remain with the Privacy-by-Design deliverable (Alicia + Luis).

**Reporting layer (decided 2026-06-14 — closes the "evaluate Juicebox replacement" item):**
- <a id="d-029"></a>Two-layer reporting architecture. Layer A (customer-facing, ~1,700 dealer tenants) and Layer B (internal authoring) both run on **Apache Superset**, self-hosted, Apache-2.0 — open-source, $0 license baseline, no mandatory commercial dependency.
- <a id="d-030"></a>Superset runs as a **headless/embedded engine**: dashboards/charts/datasets defined as YAML in git (BI-as-code), driven through the Superset REST API (chart/dashboard/dataset CRUD, `security/guest_token`, RLS endpoints). A harness / dashboard-report generator bakes into the create-chart (widget) and create-dashboard APIs.
- <a id="d-031"></a>Per-tenant isolation is **derived from our existing tenanted, privacy-by-nature data-isolation security model** — that model stays the single source of truth; the per-session guest-token RLS clause is generated from it. Reporting introduces no second isolation mechanism. Dealer onboarding is a scripted loop (one template → per-dealer guest token), not manual setup.
- <a id="d-032"></a>**Metabase Pro is an optional add-on, not core** — elected only if non-technical drag-and-drop self-serve authoring is wanted (the Juicebox-successor UX); also a possible supported commercial route for client-facing analytics. Rejected as the baseline because per-authenticated-external-viewer pricing at 1,700 dealers is ~$220K–$1M+/yr absent a negotiated Enterprise unlimited term.
- <a id="d-033"></a>**Custom-build** and **Evidence.dev** documented as alternatives for Layer A (see the Reporting Strategy artifact). Evidence's static + data-to-browser model forces build-per-tenant and code-only authoring; custom-build is best for standardized dashboards but must not rebuild the self-serve authoring surface.
- <a id="d-034"></a>Open spike before locking: confirm headless guest-token data calls (chart-data API) honor per-tenant RLS outside the Embedded SDK flow; pin Superset 6.0+; add `GUEST_TOKEN_VALIDATOR_HOOK` cross-tenant-leak guard. Owners: Alicia + Luis. Full comparison: `analysis/artifacts/reporting-strategy/`.

*Cloud & platform:*
- <a id="d-062"></a>**AWS, no Azure infra (initially).** DAS runs both; AWS chosen for data gravity (source DBs on EC2/RDS), team tooling, build home. Target is self-contained AWS. **REOPENED 2026-06-17** — client prefers consolidating on Azure-primary (see "Client-confirmed 2026-06-17" below); AWS-vs-Azure cost bake-off pending, no flip yet. Azure target = AKS + Postgres with the portable OSS core (Airflow, NATS, Temporal, OpenSearch, Postgres, Auth0, OTel) self-hosted/decoupled, avoiding proprietary SaaS.
- <a id="d-063"></a>**Portability principle:** AWS-native primary, but keep it portable to Azure/AKS with minor changes. Portable core (runs on AKS as-is): native Postgres, NATS, Temporal, k8s workloads, OpenSearch, Auth0, OTel. AWS-proprietary swap-points: MWAA (→self-host Airflow), **Redshift+zero-ETL (→Synapse/Postgres — priciest swap)**, DMS (→Debezium/Azure DMS), AMP managed Prometheus (→Azure Monitor), KMS/Secrets (→Key Vault), S3 (→Blob), ALB (→App Gateway). Isolate proprietary services behind interfaces; no vendor lock-in in app code. Redshift is the one to revisit if portability weight rises (analytics-native-Postgres is the portable alternative).
- <a id="d-064"></a>**EKS + Terraform** via `boilerworks-opscode`. Self-host NATS/Temporal/Django on EKS; MWAA managed; DB on RDS (not EKS).

Vault-row delete (`specs/.../08-pii-vault-erasure.md`) is the terminal erasure for identity-bearing data; identity inherits the same erasure semantics as consent and lifecycle rather than defining a parallel one.
- <a id="d-115"></a>**Orphan-vs-tier position (taken 2026-06-17 to close a question the lock didn't address).** Orphan identifiers (`identity_link.link_type='orphan'`) stay on **hot storage** until they become linkable — the one hot-required exception inside the tiered-lifecycle framework.
