# Facebook API Info

## Background

We use the Facebook API for multiple things. We upload Offline Conversion Event Sets, we pull ad campaign and account insights, we have some endpoints set up for Facebook webhooks, and more.

The data we pull from Facebook often ends up in Salesforce, such as the information in a Social Ad Campaign.

## What is the Facebook Graph API? What is the Facebook Marketing API?

The Facebook Graph API is the main API of Facebook. It lets us do CRUD operations on pretty much everything we would want to do.

The Facebook Marketing API is a subsection of the Graph API. The Marketing API is updated (and deprecated) much more often than the Graph API. We need the marketing API for everything having to do with campaigns, insights, and much more.

## How do I know if a DAS API method is using Facebook's Graph or Marketing API?

The Marketing API is a subsection of the Graph API. The Marketing API is called when you use these root nodes:

- `/{user}`
- `/act_{AD_ACCOUNT_ID}`
- `/{CAMPAIGN_ID}`
- `/{AD_SET_ID}`
- `/{AD_ID}`

Source: https://developers.facebook.com/docs/marketing-api/reference/v3.1

## How does our codebase hit Facebook's API?

Most of our code that hits Facebook is in the DAS API (`DAS.sln`).

There are a couple ways. The older way uses the `FacebookRequest` class, and a bunch of classes that implement that class — a class per request type (e.g. `AdCampaignInsightsRequest` → `FacebookRequest` → `Das.Infrastructure.WebClient.HttpRequest` → `HttpClient`). Versions per request are easily configured, but there is a lot more code to manage and you can never see the HTTP error message (object or null only). **`FacebookRequest` is obsolete and should not be used** — refactor callers to `FbClient.cs`.

The newer code is in `FbClient.cs` — a method per unique call, built on the third-party Facebook C# SDK (not updated in a couple of years but still works). Use `FbClient` for all new requests: simpler, and surfaces Facebook's HTTP error messages.

## PDF Reports for Social Ad Campaigns

- Generated by recurring job `SocialAdsCampaignPdfReportJob` (DAS.sln). For custom timeframes, run locally and change the dates on the Salesforce campaign query and the Facebook API query.
- Reports should be generated for any campaign with a campaign end date in the last 7 days. Active status / "Has Synch issues" don't matter; a null case reason blocks generation.
- "Website Traffic (Carousel) Campaign Results" data comes from the campaign-level Insights section.
- Campaign end date timezone gotcha: SFDC stores UTC; code uses UTC; SFDC UI displays -7. End dates near month boundaries display the wrong month on the PDF ("ending on" verbiage). Katy Wolpoff instructed her team (2/11/2019) not to schedule campaign end dates after noon in Facebook.

## How does the Facebook leadgen webhook endpoint work?

- Endpoint: `http://api.das.io/v1/facebook/webhooks/leads`
- Code: DAS.sln at `DASWebAPI/Controllers/FacebookController.cs`
- Facebook sends us leads when someone clicks on a Facebook ad (Facebook is configured to hit that endpoint). Processed by `FacebookController.cs` and **sent to Salesforce**; eventually used in Ad Campaign PDF reports sent to clients. How-to: https://digitalairstrike.atlassian.net/browse/SUS-1933
- **The leadgen endpoint also processes review information from webhooks.** Review webhooks create a Salesforce case alerting the account owner to a new Facebook review (Record Type ID `012o0000000oyri`).

## Where does the Offline Conversion data come from in the PDF reports?

- PDF reports: **account-level** data from Facebook's Account Insights API, pulled at report time to cover a full month independent of campaign dates. Direct from the Marketing API, not from SFDC Campaign Insights.
- Salesforce: **campaign-level** offline conversion data, pulled by a sync job into `Social_ads_campaign__c`. Campaign-level vs account-level: https://digitalairstrike.atlassian.net/browse/SUS-170
- Shows "Transactions within 28 days of viewing your ads" and "within 28 days of clicking your ads". Conversions are fetched for the previous month (Aug conversions visible Sep 1).
- Test helper: `GetAccountInsightsMultipleAccountsTest()`.

## Troubleshooting Loggly errors

Example: `(OAuthException - #100) Tried accessing nonexisting field (buying_type) on node type (Adgroup)`. Two usual causes: (1) field deprecated by Facebook — check the Graph/Marketing changelog and breaking changes; (2) the ID represents the wrong object type — find the call in code (e.g. `GetAdCampaignDataAsync()` expects a campaign ID), search the ID in Salesforce, or inspect via the Graph API Explorer (https://developers.facebook.com/tools/explorer/).

## Getting test IDs

Campaign ID / Ad ID: Facebook Business Manager (https://business.facebook.com) → Ads Manager → Campaigns/Ads tab → Columns → Custom → add "Campaign ID" / "Ad ID". Code's "Creative ID" = "Ad ID".

## Offline Event Sets

### General info

- Events uploaded from us to Facebook; an event typically represents a customer transaction (purchasing a car, getting service done). **We upload sales and service transaction info to Facebook as offline event sets.**
- Facebook matches ad-clickers who later appear in our offline event data → "Offline Conversions" in Ad Campaign reports.
- Visible in Business Manager → Events Manager → Offline Events. Conversions fetched for the previous month.
- **Offline Event Sets and Offline Conversions depend on sales/service transaction files (DMS files).** If transaction files are not received/processed for a client, their Offline Conversions will not work. "DMS Last Received Date" field on the Account page in Salesforce shows last receipt.

### What uploads Offline Event Sets to Facebook?

- Recurring job `SynchronizeFacebookOfflineConversions` (test: `SynchronizeFacebookOfflineConversionsTest()`).
- Each client account tracks its event set via SFDC Account field `Facebook_Offline_Conversions_Dataset_Id__c` — written by the job, never by a human. Each account should have exactly one Offline Event Set; missing Dataset Id + enabled flag for >1 day ⇒ duplicate event sets pile up in Business Manager.
- Only transactions from the **last 3 days** are fetched from Core (`ProcessAccount` in `FacebookOfflineConversions.cs`); older uploads require running locally with a changed `dataRetrievalStartDate`. Verify via Business Manager receipt time + SFDC "Facebook Offline Conversions Last Upload".
- **Auto-track limit:** each ad account allows only 10 offline event sets auto-tracking it (error 801 / subcode 2044013, "Account Reaches Offline Event Set Auto Track Limit" — broke the job in the past, SUS-980). Fix: delete duplicate/stale event sets in Business Manager until ≤9 remain.

### Endpoints used (legacy Offline Conversions API, v3.1 era)

- `POST /{businessManagerId}/offline_conversion_data_sets` — create event set (name, description)
- `POST /{eventSetId}/adaccounts` — set permissions (business manager ID, account ID)
- `POST /{dataSetId}/adaccounts` — upload offline conversions (upload tag, dataset)
