# SendGrid API Info

## Background

We use SendGrid for **transactional email delivery** across multiple DAS products and services. SendGrid is the primary email service provider for invitation emails, alert notifications, and campaign communications. The platform integrates with our Communication API, LiveJoin3 service, and Response Logix features.

SendGrid handles the delivery layer for emails generated by our applications — it's responsible for reliability, deliverability tracking, webhook event processing, and engagement metrics (opens, clicks, bounces).

## What is SendGrid?

SendGrid is a **cloud-based email delivery platform** that provides:

- **Transactional Email API** — for sending single, dynamically-generated emails (invitations, alerts, notifications)
- **Dynamic Templates** — templating engine with variable substitution and conditional content
- **Event Webhooks** — real-time notifications of email events (processed, delivered, open, click, bounce, unsubscribe, spam_report)
- **Activity Feed** — dashboard view of all sent emails with delivery status
- **Suppression Lists** — bounce and unsubscribe management
- **API Key Authentication** — simple API key-based auth (no OAuth)

SendGrid's role in DAS is **asynchronous delivery** — our services queue emails to SendGrid and receive confirmation; SendGrid handles the actual SMTP relay to recipient mail servers.

## How does our codebase hit SendGrid's API?

### Delivery Path

**Communications API** (`shared-svcs-communication-api`) is the primary integration point:
- Provides a unified interface for email, SMS (Twilio), and other channels
- Accepts email requests (recipient, template ID, dynamic data) and enqueues them to SendGrid
- Returns delivery confirmation (message ID) to caller

**LiveJoin3 Service** uses SendGrid directly:
- Sends joiner invitation emails when join rules are triggered
- Uses SendGrid's transactional email endpoint (`POST /v3/mail/send`)
- Tracks delivery status via webhook callbacks

**Response Logix** integrates via Communications API:
- Sends customer survey/follow-up emails
- Uses pre-configured templates with dealer-specific `from:` addresses

### Request Flow

```
Application → [shared-svcs-communication-api] → SendGrid (/v3/mail/send)
                                             ↓
                                        Recipient Mail Server
                                             ↓
                                          Inbox
```

Webhook responses flow in the reverse direction:

```
Recipient Action (open, click, bounce) → SendGrid Event Hook → DAS Webhook Handler
                                                               ↓
                                                    Update Mautic/CDXP contacts
```

## SendGrid API Endpoints

### Primary: Send Email

**Endpoint:** `POST https://api.sendgrid.com/v3/mail/send`

**Authentication:** API Key in `Authorization: Bearer {API_KEY}` header

**Request Body Structure:**

```json
{
  "personalizations": [
    {
      "to": [
        {
          "email": "recipient@example.com",
          "name": "Recipient Name"
        }
      ],
      "dynamic_template_data": {
        "first_name": "John",
        "dealer_name": "Valley Honda",
        "vehicle_make": "Honda",
        "review_link": "https://g.page/r/...",
        "subject_override": "Your review link"
      }
    }
  ],
  "from": {
    "email": "noreply@valleyhonda.com",
    "name": "Valley Honda"
  },
  "template_id": "d-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "tracking_settings": {
    "click_tracking": {
      "enable": true
    },
    "open_tracking": {
      "enable": true
    }
  }
}
```

**Response:** `202 Accepted`

```json
{
  "message_id": "014d3685-ba96-42f8-90b2-953231ee8d7f",
  "message": "success"
}
```

## Email Events and Engagement Tracking

SendGrid tracks six primary email events:

| Event | Meaning | DAS Action |
|-------|---------|-----------|
| `processed` | Email accepted by SendGrid, queued for delivery | Log for audit trail |
| `delivered` | Email successfully delivered to recipient mail server | Update delivery status |
| `open` | Recipient opened email (pixel-based) | Update `c_last_email_open` timestamp in CDXP; track engagement |
| `click` | Recipient clicked link in email | Update `c_last_email_click` timestamp; identify review site clicks vs. dealer website |
| `bounce` | Email rejected by recipient mail server | If `permanent` (hard bounce), set `c_email_suppressed = true` in CDXP; if `transient` (soft bounce), retry later |
| `unsubscribe` | Recipient clicked unsubscribe link | Add to suppression list; prevent future sends to this address |
| `spam_report` | Recipient marked email as spam | Add to suppression list; flag account for review |

**Timestamp:** All events include `timestamp` (Unix epoch); used to order events and correlate with user actions.

## Template Management in SendGrid

### Dynamic Templates

SendGrid templates use **Handlebars syntax** for variable substitution:

```handlebars
<h1>Hello {{first_name}},</h1>
<p>Your {{vehicle_make}} from {{dealer_name}} is ready for service.</p>
<a href="{{service_link}}">Schedule Service</a>
```

When we send an email, we pass a `template_id` (unique per template) and `dynamic_template_data` with the variables. SendGrid substitutes the values and renders the final HTML.

### Template IDs in DAS

- Each product/workflow has pre-configured template IDs stored in configuration
- **LiveJoin3** templates: joiner invite emails (mobile-optimized, branded by dealer)
- **CDXP** templates: review invitations, service reminders, followup surveys
- **Response Logix** templates: customer feedback emails

Templates are versioned in SendGrid (version history) but DAS references only the active template ID.

## Common Integration Patterns

### 1. LiveJoin Joiner Invitations

**Triggered By:** Rule evaluation in LiveJoin3 when a visitor engages with an agent

**Flow:**
1. Rocket.Chat Lead Plugin detects trigger event (customer injected, department set)
2. Sends event to LiveJoin3 Service via API
3. LiveJoin3 evaluates join rules; finds matching joiners
4. For each joiner with email, calls SendGrid API with:
   - `to:` joiner email address
   - `template_id:` joiner invite template
   - `dynamic_template_data:` joiner name, customer name, chat link
5. SendGrid returns `message_id`; LiveJoin3 logs confirmation
6. Joiner receives email with "join chat" button → clicks link → joins Rocket.Chat

**Webhook Tracking:** LiveJoin logs track `delivered` and `open` events; used for admin analytics on invite engagement.

### 2. CDXP Review Invitation Campaigns

**Triggered By:** Scheduled Mautic campaigns or contact behavior (new purchase, service completion)

**Flow:**
1. CDXP campaign sends email via Communications API
2. Communications API enqueues to SendGrid with:
   - `template_id:` CDXP review invite template
   - `dynamic_template_data:` contact name, dealer name, vehicle, review link (Google/Dealer/etc.)
3. SendGrid delivers email; webhooks fired for open/click events
4. Webhook handler parses `click` event; extracts review link URL
5. If click URL is Google/Yelp/Cars.com → updates `c_review_sent` and `c_review_link_clicked` in Mautic
6. Contact engagement metrics drive next campaign decisions (nurture non-clickers, thank clickers)

### 3. Response Logix Alert Emails

**Triggered By:** New reviews arriving in Social Logix

**Flow:**
1. Response Logix detects new low-rating review
2. Calls Communications API with alert template
3. Communications API → SendGrid with dealer account manager email, review details
4. Manager receives email; clicks review link to respond
5. Click event webhook → updates manager engagement score

## Bounce and Suppression Management

### Hard Bounces (Permanent)

**Reason:** Invalid email address, domain doesn't exist, recipient rejected due to policy

**DAS Response:**
- Set `c_email_suppressed = true` on CDXP contact
- Prevent future email sends to this address (checked before queuing)
- Alert account owner if bounce rate exceeds threshold

**Recovery:** Requires manual contact data correction or re-opt-in

### Soft Bounces (Transient)

**Reason:** Mailbox full, server temporarily unavailable, message too large

**DAS Response:**
- Log bounce event; don't suppress immediately
- Retry delivery on next campaign (within 24 hours)
- If repeated, escalate to hard bounce treatment

### Suppression Lists

SendGrid maintains **global suppression lists** per API key:
- **Bounced:** Hard bounces; emails rejected
- **Unsubscribed:** Addresses clicked unsubscribe link
- **Spam Reports:** Addresses marked email as spam
- **Invalid Emails:** Syntax errors caught by validation

Before sending, Communications API should check suppression lists to avoid wasted API calls.

## Troubleshooting SendGrid Issues

### Email Not Delivered

**Checklist:**

1. **Verify API Key** — `curl -H "Authorization: Bearer YOUR_KEY" https://api.sendgrid.com/v3/api_keys` should return 200
2. **Check SendGrid Dashboard** — Activity Feed shows sent/delivered/failed; filter by sender address or template
3. **Look for bounce classification** — If `bounce` event, read `bounce_reason` to determine root cause
4. **Verify template existence** — Template ID should be valid and active (not draft)
5. **Validate dynamic template data** — Missing variables cause rendering errors; check CloudWatch/application logs
6. **Check suppression lists** — Recipient may be on bounce list; verify via Activity Feed

### High Bounce Rate

**Common Causes:**
- **Invalid email addresses** — Contact data contains typos (e.g., "johndoe@example.cmo" instead of ".com")
- **Stale contacts** — Old email lists with addresses no longer active
- **Authentication failure** — SPF/DKIM records not configured for sender domain

**Investigation:**
- Download bounce report from SendGrid Dashboard (by date range and classification)
- Cross-reference with CDXP contact records to identify pattern (e.g., all bounces from one dealer)
- Review sender domain configuration (SPF/DKIM) in SendGrid and DNS

### Delivery Delays

**Causes:**
- **Rate limiting** — SendGrid applies IP warm-up periods for new senders; retry after 30 minutes
- **Recipient mail server slow** — Out of our control; SendGrid retries up to 72 hours
- **Large batch send** — Queue processing time; expected delay of 5-10 minutes for 10k+ emails

**Monitor:** Check `processed` and `delivered` timestamps in Activity Feed; calculate median delivery time.

## API Key Rotation and Security

### Current Key Management

- SendGrid API keys stored in application configuration (environment variables or secure vault)
- Keys are **account-level** (not per-user); single key shared across all DAS services
- **No automatic rotation** — manual process when key compromise suspected

### Best Practices

- Store API key in secrets manager (not in code or config files)
- Implement IP whitelisting in SendGrid settings (restrict which IP addresses can use the API)
- Rotate API key annually or after team member departure
- Monitor SendGrid Activity Feed for unexpected send activity

## Webhook Security

SendGrid webhooks include an **Event Webhook Authentication** header that should be verified:

**Header:** `X-Twilio-Email-Event-Signature`

**Verification:** HMAC-SHA256 signature of webhook payload using your webhook signing key (configured in SendGrid dashboard).

**DAS Implementation:**
- Webhook handler in Communications API should verify signature before processing
- Validates signature against known signing key in configuration
- Rejects unsigned or invalid webhooks (potential security threat)

## Integration Points in DAS Codebase

### shared-svcs-communication-api (dastechnology)

**Responsible for:**
- Email request validation (recipient, template, data)
- SendGrid API calls (`POST /v3/mail/send`)
- Webhook endpoint for event callbacks
- Suppression list checks before sending
- Retry logic for failed sends
- Logging and metrics

**Key Files:**
- `SendGridService.cs` (or equivalent) — SendGrid API wrapper
- `CommunicationController.cs` — webhook handler endpoint
- Configuration/secrets — API key storage

### LiveJoin3 Service (EngageToSellLLC)

**Responsible for:**
- Joiner invite email triggering
- Direct SendGrid API calls (or via Communications API)
- Delivery status logging via webhook correlation
- Joiner email preferences (opt-in/opt-out)

**Integration:**
- Calls SendGrid transactional email endpoint when join rule triggers
- Expects `message_id` in response for tracking
- Correlates webhook events with joiner records
