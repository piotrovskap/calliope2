# DAS Plan (v3 / v4) vs. CONFLICT Plan — What Changed and Why

*Phase 0 deliverable: a side-by-side of DAS's pre-discovery proposals against the plan CONFLICT recommends after Phase 0. DAS shared an **Architecture Plan v3** and an **MVP spec v4** (`artifacts/phase-0/source-docs/`), both written against assumptions before the data, identity, and infrastructure were examined. Every change below is grounded in a Phase 0 finding or a recorded decision, not in preference. The at-a-glance table is followed by the complete row-by-row reconciliation below. DAS's original v3 plan and the Phase 0 working recommendation are kept (archived, historical) at `artifacts/phase-0/deliverables/das-cdp-revised-architecture-plan.md`.*

## What we kept from DAS's Architecture Plan v3

DAS's v3 had real strengths, and we carried them forward unchanged: the **Next.js** frontend, **PostgreSQL + Row-Level Security** for multi-tenant isolation, the tiered deterministic->ML->graph resolution model (we re-sequence *when* each tier lands, not the design), the EAV + JSONB attribute shape, and cloud-portability as a core constraint. This is an evolution of v3 informed by what Phase 0 measured, not a replacement of its intent.

## What we changed, and why

| Dimension | DAS v3 / v4 proposed | CONFLICT plan | Grounded in |
|---|---|---|---|
| **Identity resolution** | AI-first: ML pairwise + GNN/embeddings + LLM triage built in from the start; "88–95% match rates" projected | Deterministic Tier-1 + human conflict queue first; ML earned in Phase 3 on real labels (schema stubs ship day-1) | DAS has no cross-system resolution today ("we don't") and no labeled corpus to train on; prove a golden record from real data first (kickoff 2026-05-27; Option A locked 2026-06-17) |
| **Ingestion source** | Broad/clean unified feed; no distinction between raw tables and pre-joined reporting views | Original sources only, explicitly **not** EDW/DWRPT; the CDP becomes the system of record | DWRPT views are manipulated/summarized, EDW is truncate-and-rebuild output (SSIS deep-dive 2026-06-08); capture raw at point of consumption (Dan, 2026-06-12) |
| **Pipeline** | Normalize-then-store; no explicit replay | Raw-first, replayable: land raw to encrypted bronze before normalize/resolve/store | Preserve untrusted source data as-received; reprocess as logic improves (decided 2026-06-18) |
| **Provenance** | Valid-time only; no system-time, no per-source history | Bitemporal append-only provenance; the "as-of" query *is* the golden-record evolution view | Mike's #1 ask: show how the record develops and which sources feed each element (2026-06-18, Alicia + Luis) |
| **Cloud** | Azure-only, all Azure PaaS (Event Hubs, Cosmos, Synapse, Azure ML/OpenAI) | Portable OSS core; Azure-primary preferred, AWS the alternative; the bake-off decides the substrate | Split estate: data gravity on AWS, apps on Azure (discovery); no vendor lock-in in app code (2026-06-17) |
| **Event bus** | Azure Event Hubs, coupled to its consumer model | Bus-agnostic NATS JetStream backbone; external buses are adapters in (Event Grid first) | DAS runs Event Grid, ownership partly unknown; avoid coupling to any one bus (2026-06-12) |
| **ETL / orchestration** | Greenfield Event Hubs/Functions/Blob; SSIS unaddressed | Airflow owns all ingest, Temporal owns app/admin; SSIS logic reimplemented against originals | 13 fragile SSIS jobs to be dropped; managed cloud-ETL (Glue/ADF) evaluated and rejected (2026-06-15) |
| **Backend language** | TypeScript/Node end-to-end (Express), Python only for offline training | Python-primary (Django + Strawberry GraphQL), Go for measured hot paths, Next.js on the frontend | Center of gravity is ML/data engineering, so Python-native; one toolchain across ingest + API + resolver (2026-06-14) |
| **Identity-graph store** | Cosmos DB (Gremlin) shadow graph synced from Postgres | Single source of truth in Postgres (`identity`/`identity_link`); Apache AGE only if traversal need is proven | A second store with 5-min sync is cost + consistency hazard that only pays off once the GNN exists |
| **Analytics / reporting** | Synapse; Juicebox left in place | Portable Postgres-centric analytics + Apache Superset (self-hosted, per-tenant RLS, $0 license baseline) | Juicebox (221 reports) is not long-term and cannot JOIN (reporting review 2026-06-08; decided 2026-06-14) |
| **Erasure** | Tokenization vault + cascading hard-delete after grace period | Keep the vault instinct, fix the delete: delete-the-row erasure; the tokenized history survives | Cascading hard-delete is incompatible with append-only provenance; row-delete reconciles right-to-erasure (2026-06-21) |
| **Auth** | NextAuth.js + Entra ID B2C | Auth0 (federates EntraID), 4-role group model; cloud-native fallback | Auth0 is already DAS-approved: it federates the same identities without standing up B2C |
| **Data model (v4 MVP spec)** | 19-table sketch | 15-table Phase-1 deployment set (11 core + 4 AI/ML stubs), all from day-1; 23-entity logical model behind it | Zero schema migrations for Phase 3 ML; table count set by the design, not by a fixed figure (locked 2026-06-18) |

## The throughline

v3/v4 were written against assumptions; this plan is written against what Phase 0 surfaced. Where v3 was sound (Postgres+RLS, portability, the resolution tiers) we kept it. Where it assumed data or infrastructure that doesn't exist yet (an AI flywheel with no training data, a clean unified feed, an all-Azure estate over AWS-resident data) we revised it to match reality. Each row cites the finding or decision behind it.

## Complete reconciliation (full rationale)

The at-a-glance table above is the quick read; this is the full row-by-row reconciliation, each change mapped to its Phase 0 finding or recorded decision. Migrated here from the Phase 0 working recommendation so the canonical diff lives in one place.

This section maps each substantive divergence between DAS's Architecture Plan v3 (March 2026) and this revised plan. Every change is grounded in a Phase 0 finding or an exec-confirmed decision — v3 was written against assumptions before discovery; this plan is written against what DAS's environment, data, and identity landscape actually surfaced. The strong parts of v3 are kept: Next.js frontend, PostgreSQL + RLS, the tiered AI resolution design, and k8s-portability.

| # | What v3 said | What we revise to | Why (Phase 0 finding / decision) |
|---|---|---|---|
| 1 | **Identity resolution is "AI-first"** — Layer 3 is "the core intelligence of the CDP," a three-tier engine where Tier 2 (ML pairwise XGBoost/ONNX) runs near-real-time and Tier 3 (128-d embeddings + GraphSAGE GNN + DBSCAN + GPT-4o LLM triage) is built into the pipeline from the start. The roadmap stands the classifier up in Phase 3 (wks 12–20) and embeddings/GNN in Phase 5 (wks 26–34). v3 projects "88–95% match rates with 98–99.5% precision." | **Deterministic Tier-1 + conflict queue first; ML earned in Phase 3 against real data.** Phase 1 ships deterministic matching (email/phone/VIN/dealer-ID normalization → exact match → link/create → human conflict queue). The 4 AI/ML tables deploy empty-but-complete in Stage 1, so ML is a config/model addition with zero schema migration. | DAS has **no cross-system identity resolution today** — their own words: "We don't." There is no labeled match/no-match corpus and no confirmed-merge history to train a classifier or embeddings on; v3's flywheel needs data that does not yet exist. Exec ask (Mike) is to **prove a golden record is achievable from DAS's real data first** ("all the people that could be Mike"), not to lead with model accuracy projections. ML is sequenced after Phase 1 generates the labeled review decisions it requires. |
| 2 | **Ingest from dealership sources broadly** via Event Hubs/Blob; v3 does not distinguish raw source tables from pre-joined reporting views, and assumes a clean unified feed. | **Original sources only — explicitly NOT EDW/DWRPT.** The CDP pulls from app DBs (EC2 SQL Server, RDS MySQL), SFTP/CSV, and vendor APIs, and *becomes* the system of record that retires EDW. | Phase 0 found DAS's `DWRPT` pre-joined views contain **manipulated/summarized data** and `EDW_*` is SSIS truncate-and-rebuild output — neither is trustworthy as an ingestion source. DAS validated this unprompted (Dan, 2026-06-12): "they don't trust CDXP/SSIS data manipulation and want the CDP capturing raw data at the point of consumption." DWRPT remains a reporting-parity *reference* only. |
| 3 | **SSIS-style batch landing** implied by the Blob/Synapse path; no explicit provenance or replay model; the `event` table keeps `raw_payload` but the pipeline is normalize-then-store. | **Raw-first, replayable ingestion.** Every channel lands raw to an **object-store bronze layer (Azure Blob / S3, encrypted)** *before* normalize→resolve→store, making the entire pipeline replayable from source-of-truth raw. | DAS's explicit requirement (Dan, 2026-06-12) is to **capture raw data at the point of consumption** (the Acceptor-lead example). Raw-first preserves untrusted source data exactly as received and lets us reprocess when normalization or resolution logic improves — critical when the resolution engine itself is being designed against real data. |
| 4 | **No bitemporal / provenance model.** v3 tracks `valid_from/valid_to` on `consumer_attribute` (valid-time only) and a `confidence_score`, but there is no system-time axis and no append-only history of which source asserted which value when. | **Bitemporal, append-only provenance** (valid-time + system-time; `valid_from/valid_to`, `recorded_at/superseded_at`, tstzrange + GiST exclusion). The "as-of" time-travel query *is* the golden-record evolution view. | Mike's #1 requested artifact is a **golden-record view showing how the record develops and which sources/events feed each element**. That requires recording every observation with both when-it-was-true and when-we-learned-it — a single valid-time field cannot answer "what did we believe about Mike on date X, and from which source." Append-only also reconciles right-to-delete via the tokenized PII vault (delete the vault row; the tokenized history stays). |
| 5 | **Azure-native, single cloud.** "Target Cloud: Microsoft Azure." All seven layers run on AKS + Azure PaaS (Event Hubs, Cosmos DB Gremlin, Synapse, Azure ML, Azure OpenAI, Azure AI Search, Entra ID B2C). | **Portable core, Azure-primary preferred.** The portable OSS core (k8s, Postgres, NATS, Temporal, OpenSearch, Auth0, OTel) deploys on either cloud; per Dan (2026-06-17) DAS prefers **Azure-primary** to consolidate on its org cloud, with AWS the alternative (data gravity on AWS source DBs). DAS's Event Grid layer is reached via a **config-only subscription → CDP webhook** (Option A) — co-located under Azure-primary, cross-cloud under AWS. The bake-off finalizes the substrate. | Phase 0 found a **split estate**: data gravity on AWS (source DBs on EC2/RDS), app/event layer on Azure (Event Grid, AKS, Functions). v3's all-Azure target ignored the AWS source DBs; an AWS-primary build would co-locate with data but cut against DAS's org-primary cloud. Rather than hard-pick, the architecture stays **portable** and the **AWS-vs-Azure bake-off** decides on per-cloud cost + gaps. The cross-cloud event subscription is config-only either way (bus-agnostic intake), not a compute footprint. |
| 6 | **Azure Event Hubs (Kafka surface)** as the unified ingestion bus; ingestion is implicitly coupled to the Event Hubs consumer model (KEDA scales on Event Hubs lag). | **Bus-agnostic intake on NATS JetStream** as the internal backbone, with external buses as **adapters in** (Event Grid first). Sources graduate batch→event through one shared validate→normalize→resolve pipeline without redesign. | Discovery found DAS already runs Event Grid (not Event Hubs as the lead) and that ownership/catalog/publishers are partly unknown. Coupling the CDP to any one bus is a liability; the design principle (CONFLICT, 2026-06-12) is a **generic bus-agnostic subscription channel with per-bus adapters** — Event Grid is "the likely first adapter, never a coupling." DAS publishes **CloudEvents 1.0** so a future direct-publish path is a config swap, not a rewrite. |
| 7 | **SSIS replacement unaddressed at the orchestration layer** — v3 assumes a greenfield Event Hubs/Functions/Blob pipeline and does not reconcile with DAS's 13 SSIS jobs. | **Airflow (managed or self-hosted) owns all ingest; Temporal owns the app/admin layer** (identity sagas, conflict-queue human-in-loop, workers). The SSIS *logic* is reimplemented against originals (Airflow DAG + Python), not ported 1:1. | Phase 0 found SSIS is **13 truncate-and-rebuild jobs, fragile and near capacity**; DAS confirmed (Dan/Mike) the jobs **"will all get dropped"** and are not a reliable end source. Managed cloud-ETL (AWS Glue / Azure Data Factory) was evaluated and rejected (moves the problem without fixing fragility). The 13 jobs are the current implementation, not the target — DAG count is set by source decomposition, not the legacy 13. Clean Airflow/Temporal split keeps ingest and app workflows from overlapping. |
| 8 | **TypeScript/Node.js backend end-to-end** — Express API, Node event workers, ONNX-in-Node ML serving, batch jobs in TS — with **Python only for offline training** in Azure ML, bridged to Node via ONNX export. | **Python-primary backend** (Django REST + Strawberry GraphQL, Airflow/Temporal workers, resolver and transform logic), **Go reserved for measured hot paths**, **Next.js/TypeScript kept on the frontend.** | This build's center of gravity is **AI/ML identity resolution and data engineering — Python-native.** v3 itself trains in Python and bridges to Node via ONNX; that seam disappears by being Python end-to-end (training, serving, resolver, batch on one runtime). Node's data/ML ecosystem is thin (no pandas/scikit/xgboost parity) and CPU-bound resolution fights its single-threaded loop. It also **unifies with the Python ingestion stack** (Airflow/Temporal) — one team, one toolchain across ingest + API + resolver, and reuse of DAS's existing Python AI layer at `ai.das-technology.com`. |
| 9 | **Express (assemble-your-own)** API — Drizzle ORM + bolt-on migrations + hand-rolled middleware. | **Django** — batteries-included ORM, migrations, admin, with expand/contract zero-downtime migrations as a Phase-1 invariant. | Surgical stack-fit consequence of #8. The build is CRUD + resolver + provenance over Postgres; Django's batteries-included ORM/migrations/admin removes the assemble-your-own overhead Express imposes, and pairs natively with the Python resolver. |
| 10 | **Cosmos DB (Gremlin) as a second identity-graph store** — a shadow graph synced from Postgres every 5 minutes and on-demand, exported nightly to feed the GNN. | **Single source of truth in Postgres.** The relational `identity`/`identity_link` tables are the graph; no separate Gremlin store. (Apache AGE on Postgres is the in-engine option if graph traversal need is proven.) | v3 itself names the Postgres `identity`/`identity_link` tables "the source of truth" and Cosmos a "shadow copy." A second datastore with 5-minute sync is operational cost and a consistency hazard that only pays off once the GNN exists (Phase 5+). With ML deferred (#1) there is no near-term consumer for a low-latency graph store; we avoid standing up Cosmos before the workload that needs it exists. |
| 11 | **Synapse Analytics** for the analytical/reporting layer; reporting strategy otherwise unaddressed. | **Postgres-based analytics (portable)** — Citus/columnar Postgres, or a cloud warehouse if the bake-off favors one; **Apache Superset** (self-hosted, headless/embedded, BI-as-code) as the reporting layer for ~1,700 dealer tenants + internal authoring. | Phase 0 found **Juicebox (221 reports) is not long-term and cannot do SQL JOINs**; the decided two-layer Superset architecture ($0 license baseline, per-tenant isolation derived from the same RLS model — no second isolation mechanism) replaces it. The analytical store is kept **portable** (Postgres-centric) rather than locked to a single-cloud warehouse — Redshift (AWS) / Synapse (Azure) are substrate options the bake-off weighs, not a dependency. |
| 12 | **PII tokenization + isolated token vault** as the erasure/privacy primitive; right-to-delete is cascading soft-delete then hard-delete after a 30-day grace period. | **Tokenized PII vault — keep v3's instinct, fix the delete.** PII centralized in a mutable vault keyed by a surrogate token; everything else (incl. the append-only bitemporal observation log) holds tokens + provenance, never raw values. Erasure = delete the vault row; the tokenized history survives. | v3's tokenization-vault instinct was right; its flaw was the *cascading hard-delete*, incompatible with the **append-only bitemporal provenance** (#4) the golden-record view requires — you cannot hard-delete history and preserve "as-of." Deleting only the vault row reconciles right-to-delete (CCPA/TDPSA) with append-only: the token history stays, only the PII the token points to is gone, and provenance (source/time/method, by token) survives. Per-consumer KMS crypto-shred was evaluated as one of the candidate mechanisms and **not chosen** (too complex, brittle, expensive); its full cost/key-lifecycle analysis is retained in `docs/consent-pii-erasure-options.md` as the design exploration the vault was iterated from. |
| 13 | **"Vehicle"** as the core asset entity; schema centers on `vehicle`/`consumer_vehicle` with VIN, make/model/year. | **"Inventory"** as the generalized asset entity. | Dan's explicit direction: generalize beyond automotive so the CDP serves **non-automotive verticals**. Naming the entity "Inventory" rather than "vehicle" keeps the data model vertical-agnostic without re-modeling later. |
| 14 | **NextAuth.js v5 + Azure Entra ID (B2C)** for auth; **NGINX Ingress + cert-manager** on AKS for the edge. | **Auth0 primary** (federates EntraID; DAS-approved SaaS), cloud-native auth fallback per substrate (Entra / Cognito), API-key/HMAC for machine ingestion; **cloud LB at the edge** (Azure Application Gateway / AWS ALB), Kong as an additive layer if the API becomes a multi-consumer product. | Phase 0 confirmed **Auth0 is already DAS-approved**, so it federates the same Entra ID identities v3 targets without standing up B2C. The cloud LB is near-zero-ops and native to whichever substrate (App Gateway on Azure / ALB on AWS); the API-gateway question (Kong) is deferred to when a multi-consumer external surface materializes, addable behind the LB without a rip-replace. |

### What we kept from v3

v3's strongest design choices carry forward unchanged: **PostgreSQL + Row-Level Security** for multi-tenant isolation, the **deterministic→ML→graph tiered resolution model** (we re-sequence *when* each tier lands, not the architecture), the **EAV + JSONB** attribute shape, the **Next.js frontend** (shadcn/ui, TanStack, the Consumer 360° / match-review / audience-builder UI surfaces), the **DAS-global-vs-dealer-isolated** data-sharing model, and **k8s-portability** as a first-class constraint. The revision is an evolution of v3 informed by what Phase 0 measured — not a replacement of its intent.

### Specified in the companion deliverables (not a v3 delta)

The data-model schema itself (final table set, the 4 AI/ML stub-table shapes, EAV+JSONB specifics, the bitemporal provenance tables), survivorship / source-trust ranking, household/family resolution, and the consent model are defined in the Identity Resolution Strategy and CDP Scoping deliverables (Alicia Salazar + Luis Hernandez), not in this comparison. The "19-table" figure in v3-adjacent material is a starting reference, not a fixed target.
