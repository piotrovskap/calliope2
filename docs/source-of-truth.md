# Source of Truth

One canonical owner per fact type. Read from the owner; do not duplicate a fact into a second file. Generated files are derived — never hand-edit them.

## Canonical owners

| Fact type | Canonical owner | Notes |
|---|---|---|
| DB status / access / owner / researcher | Per-DB frontmatter in `docs/databases/<db>.md` | The `status:` / `access:` / `owner:` / `researcher:` keys are authoritative. The README `## Status` table and `docs/databases.json` are **generated** from this frontmatter — never hand-edit them. |
| Access lifecycle / history | `analysis/artifacts/access-tracker/access.json` | The request lifecycle: how access was requested, closed, granted, or withdrawn over time. **Distinct** from the catalog's point-in-time access (see below). |
| Open asks / blockers / questions | `memory/open-questions.md` | Active asks, design questions, parked items, and the answered/closed log. |
| Decisions | `memory/decisions.md` | Decided-on positions with date and rationale. |
| Action items | `analysis/action-items.json` | Open/in-progress/done items with assignee, priority, deadline, and originating session. The subdir `analysis/artifacts/action-items/` is a render view, not the data (see Artifact stubs vs. data below). |
| RAID log | `app/raid.json` | Risks, assumptions, issues, dependencies — with severity, status, owner. |
| Engagement timeline | `analysis/artifacts/engagement-timeline/timeline.json` | Phases and steps of the engagement. |
| Golden record | `analysis/artifacts/golden-record/record.json` | Canonical CDP golden-record fields (v1.0, locked). |
| Phase / engagement status | `specs/01-phase-0-discovery/00-epic.md` frontmatter (`status:`), surfaced in the generated `specs/manifest.json` | Machine-authoritative "is Phase 0 done?" — generator-enforced, drives the board/brain. Prose mirror in `bootstrap.md` §3; the `cdp-roadmap` deliverable's `roadmap[]` state in `docs/phase0-deliverables.json` carries the phase-level chip. Keep all three in agreement. |
| UI components / design system | Storybook | Storybook is the source of truth for component behavior, visual design, states, and usage patterns. Implementations and documentation must stay aligned with it. |

The compiled **knowledge graph** ("the brain", [`knowledge-engine.md`](knowledge-engine.md)) is **not** a canonical owner of any fact. It is a generated projection that indexes and *relates* the owners above — it adds no new data, only relationships. Read a fact from its owner; query the brain for how facts connect.

## Catalog vs. tracker — two different access facts

These two must not hard-contradict, but they answer different questions:

- **Catalog** (per-DB frontmatter `access:`) = **current state.** What access we have to a DB *right now* (`granted` / `pending` / `blocked`).
- **Tracker** (`access.json`) = **how we got here.** The request lifecycle over time — when a request was opened, granted, closed, or withdrawn.

A DB can read `access: granted` in the catalog while the tracker records that the original request was *closed/withdrawn* and access was later granted anyway (e.g. DWRPT). That is consistent: catalog reflects today; tracker reflects history.

## Generated — never hand-edit

These outputs are derived from the canonical owners above. Edit the **source**, then run `make portal-generate` and commit:

| Generated file | Generated by | Derived from |
|---|---|---|
| `docs/databases.json` | `scripts/gen-databases.py` | per-DB frontmatter |
| README `## Status` table (`docs/databases/README.md`, fenced by `BEGIN/END generated` markers) | `scripts/gen-databases.py` | per-DB frontmatter |
| `docs/manifest.json` | `scripts/gen-docs-manifest.py` | docs tree |
| `specs/manifest.json` | `specs/_gen.py` | `specs/` tree |
| `app/knowledge-pack.json` | `scripts/gen-knowledge-pack.py` | knowledge markdowns |
| `app/knowledge_graph.json` (semantic KG) | `scripts/gen-kg.py` (Phase 2) | per-session graphs + `analysis/kg-curation.json` overlay |
| `docs/databases/schema.json` (DB structure) | `scripts/parse-ddl.py` (Phase 3) | `docs/databases/dumps/*.sql` |
| `docs/cdp-field-catalog.json` (CDP fields) | `scripts/gen-field-catalog.py` (Phase 3) | `docs/cdp-field-source-matrix.md`, resolved against `schema.json` |
| `app/brain.json` (compiled brain) | `scripts/gen-brain.py` (Phase 4) | all canonical owners above, via adapters |

CI's `portal-generated-clean` target (guarding `$(PORTAL_GENERATED)`: `specs/manifest.json`, `docs/manifest.json`, `docs/databases.json`, `app/knowledge-pack.json`) fails the build if any generated output is dirty — i.e. if a source changed but the regenerated output was not committed.

## Drift check

Cross-file claims are guarded by `scripts/validate-portal-data.py` (run via `make portal-schema-check`, part of `make portal-verify` in CI), which validates the hand-maintained tracker/portal JSON contracts so catalog and tracker do not structurally drift apart.

## Artifact stubs vs. data

Under `analysis/artifacts/` two files per artifact look like duplicates but are **not** — they have different roles:

- `analysis/artifacts/<id>.json` (small, ~300–600 B) is a **catalog manifest stub** — `{id, title, description, icon, href, updated}`. `analysis/index.html` reads `analysis/catalog.json`'s `artifacts[]` list, fetches each stub to render the artifact grid, and follows its `href` to the rendered view.
- `analysis/artifacts/<id>/<data>.json` (e.g. `access.json`, `timeline.json`, `record.json`) is the **canonical data** the rendered view fetches.

So the stub and the data are a render-index/data pair, not a fork — do not "dedupe" them. One anomaly: **action items** keep their data at the top level (`analysis/action-items.json`), not in the subdir; the subdir holds only the render view, which reaches back up to the top-level file. The brain (`scripts/gen-brain.py`) and trackers read the canonical data files listed above, never the stubs.
