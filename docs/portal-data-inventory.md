# Portal Data Inventory

**Goal:** Every number, status, and list shown in the portal must be driven by a data file — never hardcoded in HTML. This document is the canonical record of what is dynamic, where the source of truth lives, and how to update it.

---

## Data Files (sources of truth)

| File | Version | What it drives | Update frequency |
|---|---|---|---|
| `analysis/catalog.json` | — (Planopticon-generated) | Session count, artifact count, phase | After each session analysis |
| `docs/manifest.json` | — (auto-generated) | Doc count across all sections | After adding/removing wiki or spec docs |
| `app/knowledge_graph.json` | — (Planopticon-generated) | KG node + edge counts | After each KG rebuild |
| `activity.json` | — (git log, run `scripts/gen-activity.py`) | Recent activity feed | Before each push |
| `analysis/action-items.json` | versioned (run `scripts/gen-action-items.py`) | Global action items rollup | After each new session analysis |
| `analysis/artifacts/access-tracker/access.json` | versioned | Access tracker rows + summary counts | When access status changes |
| `docs/deliverables.json` | versioned | Deliverables gallery | When a new deliverable ships or status changes |
| `docs/phase0-deliverables.json` | versioned | Deliverable landing pages + roadmap view (`docs/deliverable.html`) | When a deliverable's status changes or scope is revised |
| `analysis/artifacts/engagement-timeline/timeline.json` | versioned | The engagement timeline (spine): every step + its output link or placeholder | When a step's status changes, a step is added, or an output ships |
| `analysis/artifacts/open-questions/questions.json` | versioned | Open Questions page: sections, items, statuses (blocker/high/medium/resolved), open/resolved counts | When a question is answered, closed, reframed, or added |
| `analysis/artifacts/golden-record/record.json` | versioned | Golden Record view: sections, elements, tiers (core/valuable/later/tbd), statuses (pending/draft/validated), feeding sources | As the identity design lands — element by element |
| `analysis/artifacts/identity-strategies/strategies.json` | versioned | Identity strategy options: comparison axes, option cards, recommendation | As strategy options are drafted and one is selected |
| `analysis/artifacts/reporting-strategy/strategy.json` | versioned | Reporting-layer strategy: comparison axes, option cards (Superset/custom-build/Evidence/Metabase), recommendation, architecture fit, open items | When the reporting-layer decision changes or the open spike resolves |
| `app/raid.json` | versioned | RAID Log: risks, assumptions, issues, dependencies (id, type, severity, status, owner, mitigation, source) | When a risk/assumption/issue/dependency is added, resolved, or its status/decision changes |
| `app/knowledge-pack.json` | — (run `scripts/gen-knowledge-pack.py`) | Chat agent's search index (path/title/summary per doc) | After adding/removing/renaming knowledge markdowns; before deploy |

**Versioned files** have a `version` (integer, increment on each change), `updated` (YYYY-MM-DD), and `changelog` array. Always update all three fields together.

## Where each file is consumed

### `analysis/catalog.json`
- `index.html` — stat strip (phase, sessions, artifacts), Sessions card count + tag, Reference card artifact count tag
- `analysis/index.html` — session list, artifact list
- `analysis/artifacts/index.html` — artifact index grid (directory landing page; loads each `artifacts/{id}.json`)

#### Session count semantics (three scopes, by design — do not "reconcile" to one number)
Three files count sessions for three different purposes; the numbers legitimately differ:
- **`analysis/catalog.json` → 3** — the **Planopticon deep-analysis sessions** (full transcript analysis + artifacts). This is the **portal** session count/listing.
- **`analysis/sessions/catalog.json` → 4** — the **KG transcript-source sessions** (kickoff, kickoff-rec, reporting, ssis-review) that feed `gen-kg.py` and the brain's Session nodes.
- **action-item sessions → 6** — every `analysis/sessions/*/results/action_items.json` dir, including lighter touchpoints (exec-sync, architecture-design) that are neither deep-analysis nor KG transcript sources.
Each file is authoritative for its own scope; none should be edited to match the others.

### `docs/manifest.json`
- `index.html` — docs stat, Documentation card description + tag, hero description
- `docs/index.html` — doc browser index

### `app/knowledge_graph.json`
- `index.html` — entities stat, Intelligence card description + tags

### `analysis/action-items.json`
- `analysis/artifacts/action-items/index.html` — global action items table with priority filter and session filter
- Generated by `scripts/gen-action-items.py` — aggregates all `analysis/sessions/*/results/action_items.json` files

### `activity.json`
- `index.html` — Recent Activity feed

### `analysis/artifacts/access-tracker/access.json`
- `analysis/artifacts/access-tracker/index.html` — full table + auto-computed summary strip
- `index.html` — Status card "N access items" tag

### `docs/deliverables.json`
- `deliverables/index.html` — deliverables gallery cards

### `docs/phase0-deliverables.json`
- `docs/deliverable.html` — one template that renders every deliverable + sub-component by `?id=` (e.g. `?id=cdp-roadmap`, `?id=cdp-roadmap.identity-resolution`); the `cdp-roadmap` deliverable also renders the roadmap view from its `roadmap` array. Optional `md`/`pdf` fields surface format-download links (Markdown = source, PDF = final) when present
- `analysis/artifacts/engagement-timeline/index.html` — composes deliverable status/title/summary live into the timeline's Deliverables group
- `deliverables/index.html` — composes the scaffolded deliverables into the gallery (cards linking to `deliverable.html?id=`), alongside the shipped items from `deliverables.json`

### `analysis/artifacts/engagement-timeline/timeline.json`
- `analysis/artifacts/engagement-timeline/index.html` — renders the whole timeline (phase strip + grouped steps). Each step either references an existing `output` (session/artifact page), a `deliverable` id (composed from `phase0-deliverables.json`), or neither → links to `step.html?id=` placeholder
- `analysis/artifacts/engagement-timeline/step.html` — renders the placeholder page for any pending step (status, "what it produces", format links when files land)

---

### `analysis/artifacts/reporting-strategy/strategy.json`
- `analysis/artifacts/reporting-strategy/index.html` — renders comparison axes, option cards, recommendation, and the architecture-fit + open-items lists
- Companion `decision-process.md` in the same folder is a static methodology record + scrubbed working-session log

### `app/raid.json`
- `raid/index.html` — renders the RAID Log (risks / assumptions / issues / dependencies as cards). Linked from the command-center nav (`index.html`)

## What is intentionally static (historical record)

These pages contain hardcoded data that reflects a point-in-time record and is not expected to change:

| Page | Static content | Why it's OK to leave it |
|---|---|---|
| `analysis/artifacts/engagement-timeline/index.html` | Session dates, milestone names, phase labels | Timeline is a historical artifact; edit it when phases change |
| `analysis/artifacts/open-questions/index.html` | Question text, session references, specific counts (Mileone 20 runs, etc.) | Questions are logged at time of session; new questions get new entries |
| `analysis/artifacts/ssis-job-catalog/index.html` | 13 job rows, KPI strip, failure notes | Snapshot of SSIS state at 2026-06-08; will be superseded by a new session artifact if SSIS changes materially |
| `analysis/sessions/*/results/analysis.html` | All content | Generated by Planopticon — regenerate via `planopticon analyze` if needed |
| `analysis/sessions/session-synthesis-2026-06-08.html` | All content | Session synthesis is a dated artifact |
| `knowledge/index.html` | "221 reports", "14 CDXP-Live", session links | Intelligence hub is a curated index — update manually when sessions are added |
| `reference/index.html` | "4 artifacts", "13 jobs" | Reference section cards are curated — update when artifacts are added |

## How to update versioned files

### access.json — access status changed
1. Edit `analysis/artifacts/access-tracker/access.json`
2. Update the `status` field on the relevant item (`granted` | `committed` | `pending` | `blocked`)
3. Update `detail` with what changed
4. Bump `version`, set `updated` to today, append to `changelog`
5. Commit: `git add analysis/artifacts/access-tracker/access.json && git commit -m "chore(access): update [resource] → [new status]"`

### deliverables.json — new deliverable shipped
1. Edit `docs/deliverables.json`
2. Append to `items` array with `title`, `type`, `typeClass`, `status`, `statusClass`, `date`, `desc`, `open`, `preview`
3. Bump `version`, set `updated`, append changelog entry
4. Commit: `git add docs/deliverables.json && git commit -m "feat(deliverables): add [title]"`

### activity.json — before pushing
```bash
python3 scripts/gen-activity.py
git add activity.json
```

## Adding a new data file

When a new page needs dynamic data:
1. Create `your-data.json` with `version: 1`, `updated`, `changelog`, and your data
2. Fetch it client-side in the consuming HTML page
3. Add an entry to this inventory doc
4. Add an update instruction block above
5. Add a row to this inventory and note the change in `memory/MEMORY.md`
6. Commit all four changes together

## Versioning convention

```json
{
  "version": 2,
  "updated": "2026-06-12",
  "changelog": [
    {"date": "2026-06-12", "note": "DWRPT access granted by Ron"},
    {"date": "2026-06-09", "note": "Initial extraction from hardcoded HTML"}
  ]
}
```

- `version`: integer, increment on every meaningful data change
- `updated`: ISO date of last change
- `changelog`: newest entry first; one line per change, enough context to understand what shifted without reading the full diff
